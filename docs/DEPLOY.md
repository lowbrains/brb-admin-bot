# Выкладка на сервер

Целевая машина: **VM Timeweb в российской локации**. Выбор не косметический — см.
«Почему сервер российский».

## Порядок

### 0. Замер до всего остального

На сервере, до установки чего-либо:

```bash
curl -m 10 -o /dev/null -w "telegram %{http_code}\n" https://api.telegram.org/bot123456:FAKE/getMe; curl -m 10 -o /dev/null -w "openai   %{http_code}\n" https://api.openai.com/v1/models
```

Ожидается `401` на обоих: адрес ответил, ключ фальшивый. `000` означает, что
ответа не было — тогда этому адресату нужен прокси (`TELEGRAM_PROXY` или
`MODEL_PROXY` соответственно), и до выяснения дальше идти не надо.

### 1. Поставить Docker и забрать код

```bash
curl -fsSL https://get.docker.com | sh
git clone git@github.com:<owner>/brb-admin-bot.git /opt/brb-admin-bot
cd /opt/brb-admin-bot
```

### 2. Прокси — на сервере в Нидерландах не нужен

Обе переменные маршрута остаются пустыми. Этот шаг появится, только если шаг 0
даст `000` по какому-то адресату — например, при переезде на российский сервер,
где недоступен уже OpenAI. Тогда нужен внешний HTTP-прокси, и в `.env`
заполняется соответствующая переменная:

```
TELEGRAM_PROXY=http://логин:пароль@узел:3128
MODEL_PROXY=http://логин:пароль@узел:3128
```

Проверка, что прокси жив:

```bash
curl -m 10 -x "$MODEL_PROXY" -o /dev/null -w "%{http_code}\n" https://api.openai.com/v1/models
```

### 3. Заполнить окружение и данные

```bash
cp .env.example .env && chmod 600 .env
```

`runtime/` в репозитории нет — он в `.gitignore`. Каталог надо создать **и отдать
пользователю контейнера**: процесс работает не от root, а от `uid 10001`, и на
свежесозданном root-каталоге получит `Permission denied` при первой же записи в базу.

```bash
mkdir -p runtime/config runtime/data
sudo chown -R 10001:10001 runtime
```

> На macOS этой ошибки не видно — Docker Desktop транслирует UID. Проявляется только
> на Linux, то есть ровно на сервере. Проверено 14.09.2026.

Содержимое переносится отдельно (scp, не через git и не через мессенджер):

```
runtime/team.txt
runtime/config/discussion-config.json
runtime/config/connection.json          # либо BRB_CHAT_ID в .env
runtime/data/                           # если переносится накопленная переписка
```

### 4. Остановить ноутбучную копию

**До первого запуска контейнера.** Два приёмника `getUpdates` одновременно — это
HTTP 409 и потерянные сообщения. Закрыть окно `start.cmd` / `start-ai.cmd` на ноутбуке.

### 5. Запуск

```bash
docker compose up -d --build
docker compose logs -f bot
```

### 6. Проверка на живой группе

Шаги по возрастанию риска; первый отказ — остановиться и разобраться.

1. `docker compose ps` — `Up`, без цикла перезапусков.
2. В журнале: `Обсуждения: запущено.`
3. В группе `/ping` → «На связи. Режим обсуждений включён.»
4. `/team` → список из девяти человек.
5. Обычное сообщение → ответа нет (и не должно быть), но оно попало в базу:
   `docker compose exec bot python -c "import sqlite3;print(sqlite3.connect('/runtime/data/discussion.sqlite3').execute('select count(*) from messages').fetchone())"`
6. `@brb_team_admin_bot подведи итог` → осмысленный ответ. **Это первый вызов модели** —
   если маршрутизация неверна, отвалится именно здесь.
7. «зафиксируй поручение …» → карточка с кнопками → «Записать» → `/tasks` показывает её.

До пункта 7 подключение считать неподтверждённым.

## Почему так

Сервер стоит в **Нидерландах** — на нём уже работает `businessincognita-digest`,
который ходит напрямую в OpenAI. Оттуда доступны и Telegram, и OpenAI, поэтому
прокси не нужен ни для чего и обе переменные маршрута остаются пустыми.

Яндекс на этой площадке недоступен — замер 14.09.2026 с зарубежного выхода:

```
api.telegram.org:443           HTTP 401 за 0,74 с   — доступен
ai.api.cloud.yandex.net:443    TCP не отвечает, таймаут 15 с
storage.yandexcloud.net:443    отвечает             — блокировка выборочная
```

Отсюда и смена провайдера на OpenAI: она снимает конфликт маршрутов целиком,
а не разводит его прокси.

Цена решения нетехническая и принята осознанно: переписка группы БРБ и ФИО
девяти сотрудников ГПН обрабатываются зарубежной моделью на зарубежном сервере.
Модели передаётся не вся переписка, а последние 60 сообщений при обращении к
боту; `store: false` отключает сохранение ответов на стороне провайдера.

## Чего в этой сборке нет

- **Нет сигнала «бот жив, но глухой».** Если Telegram недоступен, процесс не падает,
  а бесконечно печатает «Нет связи с Telegram» — контейнер остаётся `Up`, сообщения
  не обрабатываются. Нужен heartbeat и healthcheck поверх него.
- **Нет резервного копирования** `runtime/data/discussion.sqlite3`. Том переживает
  пересборку, но не удаление VM.
- **Нет очереди доставки.** При сетевом обрыве статус отправки остаётся неопределённым,
  повтор вручную — так задумано автором, чтобы не дублировать поручения.
- **Модель не проверена живым запросом.** `gpt-5-mini` взята как заведомо рабочая
  в этом аккаунте — на ней работает `businessincognita-digest`. Единственный
  сомнительный параметр в payload — `temperature: 0.3`: модели семейства GPT-5
  могут не принимать нестандартное значение. Если запрос вернёт 400 с жалобой
  на `temperature`, лечится удалением одной строки в `ask_model`.
