# Выкладка на сервер

Целевая машина: **VM Timeweb в российской локации**. Выбор не косметический — см.
«Почему сервер российский».

## Порядок

### 0. Замер до всего остального

На свежем сервере, до установки чего-либо:

```bash
curl -m 10 -o /dev/null -w "telegram  %{http_code}\n" https://api.telegram.org/bot123456:FAKE/getMe
curl -m 10 -o /dev/null -w "yandex    %{http_code}\n" -X POST -H 'Content-Type: application/json' \
     -d '{}' https://ai.api.cloud.yandex.net/v1/responses
```

Что означает результат:

| telegram | yandex | Вывод |
|---|---|---|
| `401` | `401`/`400`/`403` | Оба адреса доступны. Прокси не нужен, `TELEGRAM_PROXY` оставить пустым. |
| `000` | `401`/`400`/`403` | Ожидаемый случай. Нужен прокси только для Telegram — шаг 2. |
| `401` | `000` | Сервер оказался не в РФ. Остановиться и пересмотреть выбор площадки. |

`401` — это успех: адрес ответил, просто ключ фальшивый. `000` — ответа не было вовсе.
**Без этого замера архитектуру не выбирать.**

### 1. Поставить Docker и забрать код

```bash
curl -fsSL https://get.docker.com | sh
git clone git@github.com:<owner>/brb-admin-bot.git /opt/brb-admin-bot
cd /opt/brb-admin-bot
```

### 2. Прокси для Telegram — только если шаг 0 дал `000`

Три рабочих варианта, выбирается по тому, какой выходной узел есть в наличии.
Конкретный не зашит в репозиторий намеренно: узел пока не выбран, а угаданный
конфиг хуже отсутствующего.

**а) Готовый внешний HTTP-прокси.** Ничего разворачивать не нужно:

```
TELEGRAM_PROXY=http://логин:пароль@узел:3128
```

**б) Свой VPS за границей.** На нём — 3proxy или tinyproxy, слушает только адрес
российского сервера (firewall по IP, не открытый прокси). В `.env` — его адрес.

**в) WireGuard до зарубежного узла.** Сайдкар-контейнер поднимает WG и отдаёт
HTTP-прокси во внутреннюю docker-сеть; бот ходит в него по имени сервиса.
Маршрут по умолчанию на сервере **не трогать** — иначе в туннель уедет и Яндекс,
и вся схема теряет смысл.

Проверка после настройки — прокси отвечает и отдаёт заграничный адрес:

```bash
curl -m 10 -x "$TELEGRAM_PROXY" -o /dev/null -w "%{http_code}\n" https://api.telegram.org/bot123456:FAKE/getMe
```

### 3. Заполнить окружение и данные

```bash
cp .env.example .env && chmod 600 .env
```

`runtime/` в репозитории нет — он в `.gitignore`. Содержимое переносится отдельно
(scp, не через git и не через мессенджер):

```
runtime/team.txt
runtime/config/discussion-config.json
runtime/config/connection.json          # либо BRB_CHAT_ID в .env
runtime/data/                           # если переносится накопленная переписка
```

### 4. Остановить ноутбучную копию

**До первого запуска контейнера.** Два приёмника `getUpdates` одновременно — это
HTTP 409 и потерянные сообщения. Закрыть окно `start.cmd` / `start-ai.cmd` на ноутбуке.

### 5. Запуск

```bash
docker compose up -d --build
docker compose logs -f bot
```

### 6. Проверка на живой группе

Шаги по возрастанию риска; первый отказ — остановиться и разобраться.

1. `docker compose ps` — `Up`, без цикла перезапусков.
2. В журнале: `Обсуждения: запущено.`
3. В группе `/ping` → «На связи. Режим обсуждений включён.»
4. `/team` → список из девяти человек.
5. Обычное сообщение → ответа нет (и не должно быть), но оно попало в базу:
   `docker compose exec bot python -c "import sqlite3;print(sqlite3.connect('/runtime/data/discussion.sqlite3').execute('select count(*) from messages').fetchone())"`
6. `@brb_team_admin_bot подведи итог` → осмысленный ответ. **Это первый вызов модели** —
   если маршрутизация неверна, отвалится именно здесь.
7. «зафиксируй поручение …» → карточка с кнопками → «Записать» → `/tasks` показывает её.

До пункта 7 подключение считать неподтверждённым.

## Почему сервер российский

Замер от 14.09.2026 с зарубежного выхода (Казахстан, AS203087):

```
api.telegram.org:443           HTTP 401 за 0,74 с   — доступен
ai.api.cloud.yandex.net:443    TCP не отвечает, таймаут 15 с
llm.api.cloud.yandex.net:443   TCP не отвечает
storage.yandexcloud.net:443    отвечает             — блокировка выборочная, не «весь Яндекс»
```

Это один конкретный выход, а не «любой VPN». Но направление ясно: LLM API Яндекса
с зарубежного адреса недоступен на уровне TCP.

С российского сервера картина обратная и лучше: Яндекс — напрямую, быстро, без
анти-фрода, переписка ГПН не пересекает границу. В туннель уходит только Telegram,
куда те же сообщения идут в любом случае.

Зарубежные модели (OpenAI, Anthropic, Google) сами блокируют российские адреса,
поэтому смена провайдера на этой площадке не упрощает схему, а загоняет в туннель
**оба** канала вместо одного.

## Чего в этой сборке нет

- **Нет сигнала «бот жив, но глухой».** Если Telegram недоступен, процесс не падает,
  а бесконечно печатает «Нет связи с Telegram» — контейнер остаётся `Up`, сообщения
  не обрабатываются. Нужен heartbeat и healthcheck поверх него.
- **Нет резервного копирования** `runtime/data/discussion.sqlite3`. Том переживает
  пересборку, но не удаление VM.
- **Нет очереди доставки.** При сетевом обрыве статус отправки остаётся неопределённым,
  повтор вручную — так задумано автором, чтобы не дублировать поручения.
- **Конфигурация модели не проверена живым запросом.** `ai.api.cloud.yandex.net/v1/responses`,
  модель `aliceai-llm`, и заголовок `OpenAI-Project` с folder-id вместо привычного
  `x-folder-id`. Проверяется пунктом 6 шага 6 — не раньше.
